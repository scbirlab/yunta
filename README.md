**`yunta`** provides several implementations of protein-protein interaction evaluation. In increasing computational cost:

- GPU-accelerated direct coupling analysis (DCA) in PyTorch
- [RoseTTAFold](https://github.com/RosettaCommons/RoseTTAFold)-2track via the `rf2t-micro` package
- [AlphaFold2](https://github.com/google-deepmind/alphafold) for protein-protein structure prediction

`yunta` has streamlined installation, a command-line interface, a Python API, and resilience to GPU out-of-memory errors through chunking of long sequences and CPU-fallback. It takes as input unpaired multiple-sequence alignments in A3M format (as generated by tools like [`hhblits`](https://github.com/soedinglab/hh-suite)), and outputs a matrix of inter-residue contacts.

## Installation

```bash
pip install yunta
```

To enable AlphaFold2 with CUDA 12 (recommended for GPU):

```bash
pip install yunta[af_cuda12]
```

For a local CUDA 12 installation:

```bash
pip install yunta[af_cuda12_local]
```

For CUDA 11:

```bash
pip install yunta[af_cuda11]
```

For AlphaFold2 without a specific CUDA version (CPU or custom JAX install):

```bash
pip install yunta[af]
```

To enable RosettaFold-2track:

```bash
pip install yunta[rf2t]
```

Using the embedded models requires the [RoseTTAFold](https://github.com/RosettaCommons/RoseTTAFold)-2track and AlphaFold2 weights. These are automatically downloaded on first use. By doing so you agree that the trained weights for RoseTTAFold are made available for non-commercial use only under the terms of the [Rosetta-DL Software license](https://files.ipd.uw.edu/pub/RoseTTAFold/Rosetta-DL_LICENSE.txt) and AlphaFold2's pretrained parameters fall under the [CC BY 4.0 license](https://creativecommons.org/licenses/by/4.0/legalcode).

## Credit

`yunta` is a fork of [SpeedPPI](https://www.biorxiv.org/content/10.1101/2023.04.15.536993v1), which is itself inspired by [FoldDock](https://www.nature.com/articles/s41467-022-28865-w). This method used AlphaFold2 to evaluate 65,484 protein-protein interactions from the human proteome in [Towards a structurally resolved human protein interaction network](https://www.nature.com/articles/s41594-022-00910-8).

The idea of using DCA, [RoseTTAFold](https://github.com/RosettaCommons/RoseTTAFold)-2track, and [AlphaFold2](https://github.com/google-deepmind/alphafold) in a cascade of increasingly expensive and specific PPI detection methods has been explored in a series of papers from David Baker's lab:

- [Cong et al., Protein interaction networks revealed by proteome coevolution. _Science_, 2019](https://doi.org/10.1126/science.aaw6718)
- [Humphreys et al., Computed structures of core eukaryotic protein complexes. _Science_, 2021](https://doi.org/10.1126/science.abm4805)
- [Humphreys et al., Protein interactions in human pathogens revealed through deep learning. _Nature Microbiology_, 2024](https://doi.org/10.1038/s41564-024-01791-x)

`yunta` puts these algorithms in one place with easy installation, a command-line interface, and a Python API. It also enables interspecies co-evolutionary analysis using a built-in host-pathogen interaction mapping.

## Memory and speed

**DCA.** DCA prunes residue states never seen at a site (exact), computes sequence weights and the covariance in
tiles (the M x M identity matrix is never built), streams the alignment in row slabs (so deep alignments never hold
the whole one-hot matrix), inverts by Cholesky (LU as a fallback) and accumulates coupling norms tile by tile. The
straight port is kept as `_calculate_dca_reference`; `benchmarks/bench_dca.py` compares the two, and the tests check
that they agree.

For AF2 the training-only heads are off, the MSA is padded to its real depth (bucketed; same outputs, fewer compiles),
`--subbatch-size N` trades speed for memory in attention, `--unified-memory` lets the GPU spill into
host RAM (set before JAX starts), and `--fixed-msa-padding` restores stock padding. Compiled programs are
cached on disk (`YUNTA_JAX_CACHE`). `--recycle-tolerance A` drives recycling from Python (the Evoformer then compiles
once instead of twice) and stops early once the C-alpha distance matrix changes by less than A angstrom between
passes; it is approximate, off by default, and `0` reproduces the stock result. Details: `benchmarks/af2_optimisations.md`.


## `pair` and `coevo` (recommended interface)

Pairing and prediction are separate steps. `coevo` pairs once per protein pair, so several methods
share the pairing, and each model is loaded once per run (and released afterwards).

```bash
# Real pairing, and a negative control that keeps depth and per-species multiplicity but
# removes every known interacting species pair
yunta pair A.a3m --msa2 B.a3m --interspecies --pairing map      -o paired/
yunta pair A.a3m --msa2 B.a3m --interspecies --pairing rewired  --seed 1 -o paired/

# Predict from exactly that saved pairing (the .json sidecar written by `pair` holds the chain
# boundary, pairing method, seed and diagnostics) ...
yunta coevo paired/A-B.rewired.a3m --paired -m dca af2 of3 -o results/

# ... or pair and predict in one go; the control seed is recorded in the metrics
yunta coevo A.a3m --msa2 B.a3m --pairing rewired -m dca af2 of3 --structures models/ -o results/
```

**Controls.** `--pairing`: `map` (default), `rewired` (degree-preserving rewiring of the species-pair
graph, Maslov & Sneppen 2002, known pairs forbidden), `random-species` (pairs drawn from outside the
map), `random-rows` (rows matched at random, known species pairs rejected) and `permute-partners`
(the real rows and gap patterns, with the partner chain's rows permuted so no known pair survives; it
keeps composition and per-chain gaps, so it isolates *who is paired with whom*). Each control is
checked for its invariants twice: as generated, and again on the alignment that is actually scored
(after the gap filter), against the real pairing put through the same filter: depth, species pairs
retained from the real pairing, per-species multiplicity (`rewired`) and per-chain row composition
(`permute-partners`) are re-measured on the final alignments. `permute-partners` gap-filters the *real*
rows first and permutes exactly the survivors, so its final A and B rows are the real ones; the permuted
rows are never refiltered, so their joint gap fraction can differ from the real rows'. A control with surplus
rows is trimmed (seeded) to the real final depth; one that falls short is invalid. Invalid controls are
an **error by default** (in batches the pair is skipped and listed in `CoevoPredictor.rejected`);
`--allow-invalid-controls` downgrades that to `pairing_valid=False`. The rejection rate and its reasons are logged (`[INFO] Negative control ...: n/N pairs rejected`, with a
warning when most are rejected): check it before comparing real and control scores, because rejected pairs are
missing from the control set. The metrics carry `pairing_*`
columns, including final depth, Neff and mean gap for the control and its reference. Score the real
pairing against several control replicates (different `--seed`s). A score that does not exceed the control
distribution is insufficient evidence for pairing-specific coevolution: weak coupling, model sensitivity,
stochastic variation, too few effective sequences or poor predictions could each explain it. A score
that does exceed it is not, by itself, evidence of a physical interaction, because shared phylogeny can
also generate correlated variation between families (see `yunta/structs/pairing.py`).

**Scores.** AF2 and OpenFold3 report per-chain/interface pLDDT, pDockQ, pDockQ2, pTM, ipTM, actifpTM, ipSAE, LIS
and mean inter-chain PAE. Every score is computed by the same code (`yunta/interactions/confidence.py`) from one
canonical record that each backend hands over (pLDDT on a 0-100 scale, PAE bin probabilities, contact probability);
unit mistakes (a 0-1 pLDDT, logits instead of probabilities, PAE not in Angstrom) raise instead of skewing a score.
So `iptm` means the same thing whichever model produced it. pTM and ipTM are recomputed from the PAE bin
probabilities rather than taken from the model; the models' own values are kept for cross-checking
(`ptm_af2`; `ptm_model` and `iptm_model` for OpenFold3). OpenFold3 computes the PAE probabilities and contact
probabilities but does not save them, so yunta switches on the settings that keep them and captures them from its output
writer; if that capture fails, pTM, ipTM and actifpTM are `NaN` (a warning says so) and the rest still work.
pDockQ2, ipSAE and LIS follow the original papers and Dunbrack's `ipsae.py`; pTM/ipTM are tested against the AlphaFold reference.

**Whole vs blockwise.** Chunking is opt-in: by default (`chunksize=None`, no `--chunksize`) the whole complex
is modelled in one call, and a warning is printed if the estimated memory exceeds what is free. With
`--chunksize N`, an alignment longer than `N` is split into blocks that are modelled independently, and the metrics say `score_mode=blockwise`. Blockwise scores are
approximations built from independent sub-models, not values for any one physical complex; they are
not comparable with `score_mode=whole`. Structure backends only run inter-chain blocks and write no
PDB when chunked; pTM, ipTM and actifpTM need a single model and are `NaN` when chunked. For DCA the
approximation was measured on real yeast MSAs (`benchmarks/chunked_vs_full_dca.py`): Spearman
0.82-0.89 to the unchunked matrix, 42-66% overlap in the top 50 residue pairs, and chunked scores
about 1.8-3.6x more spread out, so do not mix chunked and unchunked DCA scores.

See "Memory and speed" above for the memory options that usually make chunking unnecessary.

**OpenFold3 status.** The OpenFold3 backend is tested against a stand-in model and the 0.5.1 API only; it has not yet
been run on a GPU with real weights (the gated smoke test `test/test_of3_gpu_smoke.py`, enabled with
`YUNTA_OF3_SMOKE=1`, is pending). It stays behind its optional dependency until that has run.

**Structures.** `--structures DIR` writes a PDB for AF2 and OpenFold3 (also `structure=True` in Python,
returned as `metrics.structure`). Only for whole-complex calls: never for a chunked complex.

### Parallel jobs and weight downloads

Weight downloads (AlphaFold2 parameters, OpenFold3 checkpoint) are single-flight: when many
processes start at once on a shared filesystem, one downloads while the others wait on a
[`filelock`](https://py-filelock.readthedocs.io/) next to the target file, then reuse the result.
Files appear by atomic rename, so no process can load a half-written file, and a killed
download releases its lock automatically. Set `YUNTA_DOWNLOAD_TIMEOUT` (seconds) to stop
waiting eventually, and `YUNTA_LOCK_TYPE=soft` on filesystems without `flock` support (a soft
lock left by a crashed job must then be deleted by hand). Set `YUNTA_JAX_CACHE=/shared/dir` to
share AlphaFold2's compiled XLA programs between workers. RoseTTAFold2t weights are fetched by
`rf2t-micro` itself and are not covered by this lock.

OpenFold3 (`pip install "yunta[of3]"`) downloads its default weights on first use to
`$OPENFOLD_CACHE` or `~/.openfold3`; use `--of3-checkpoint` for your own. Only the paired MSA is
given to the model (no MSA server, no templates), so any signal comes from the pairing. The query
schema and runner arguments are checked against the real OpenFold3 package in
`test/test_of3_real_api.py`; the model itself has not been run end-to-end here.

The older `dca-*`, `rf2t-*` and `af2-*` commands remain for compatibility.

```bash
options:
  -h, --help            show this help message and exit

Sub-commands:
  {dca-single,dca-many,rf2t-single,af2-single,af2-many}
                        Use these commands to specify the tool you want to use.
    dca-single          Calculate DCA for one protein-protein interaction.
    dca-many            Calculate DCA between two sets of proteins, or all pairs in one set of proteins.
    rf2t-single         Calculate RF-2track contacts between one protein and a series of others.
    af2-single          Model one protein-protein interaction.
    af2-many            Model all interactions between two sets of proteins, or all pairs in one set of proteins.
```

### Generating multiple-sequence alignments

All algorithms depend on pre-computed multiple-sequence alignments (MSAs) between a protein of interest and as many homologs as possible. You can generate MSAs using [`hhblits`](https://github.com/soedinglab/hh-suite) with pre-clustered databases like UniClust:

```bash
hhblits -e 0.01 -v 3 -d /path/to/UniClust-database -i input.fasta -oa3m output-msa.a3m -o /dev/null -cov 60 -n 3 -realign -realign_max 10000
```

This typically takes 1–40 min depending on query complexity. See the [`hhsuite`](https://github.com/soedinglab/hh-suite) documentation for details.

### Calculating contact maps

Given two MSAs, `yunta` calculates a contact map using DCA, RF2t, or AlphaFold2, and produces a summary table for each pair.

Using DCA or RF2t produces a table like this:

```bash
$ yunta dca-single test/inputs/DYR_YEAST.a3m -2 test/inputs/CAPZA_YEAST.a3m -o test/outputs/dca-single.tsv --apc
```

| ID | uniprot_id_1 | uniprot_id_2 | seq_len | chain_a_len | chain_b_len | msa1_depth | msa2_depth | msa_depth | n_eff | DCA:apc | DCA:mean | DCA:median | DCA:maximum | DCA:minimum | DCA:var | DCA:sigma1 | DCA:focality | DCA:top_A | DCA:top_B |
| -- | ------------ | ------------ | ------- | ----------- | ----------- | ---------- | ---------- | --------- | ----- | ------- | -------- | ---------- | ----------- | ----------- | ------- | ---------- | ------------ | --------- | --------- |
| O13297-D6VTK4 | O13297 | D6VTK4 | 980 | 549 | 431 | 14246 | 1546 | 670 | 2 | False | 0.0183 | 0.0147 | 0.0743 | 2.28e-06 | ... | ... | ... | ... | ... |

Method-specific columns are prefixed with `DCA:` or `RF2t:`. Common columns across all methods:

- `sigma1` — leading singular value of the inter-chain contact submatrix
- `focality` — ratio of first to second singular value; higher values indicate a more concentrated interaction signal
- `top_A`, `top_B` — indices of the top-scoring residues in each chain (from the leading SVD eigenvector)

If you also give `--plot`, contact maps for the full complex and inter-chain contacts only are saved as PNG, alongside CSV files of the raw matrices:

```bash
$ yunta dca-single test/inputs/DYR_YEAST.a3m -2 test/inputs/CAPZA_YEAST.a3m -o test/outputs/dca-single.tsv --apc --plot test/outputs/DYR_YEAST-CAPZA_YEAST
```

### Predicting protein complex structures

`yunta` can feed MSAs into AlphaFold2 to predict binary protein complex structures:

```bash
$ yunta af2-single test/inputs/DYR_YEAST.a3m -2 test/inputs/CAPZA_YEAST.a3m -o test/outputs/af2-single.tsv
```

This writes a summary TSV with `AF2:`-prefixed metrics — `n_contacts`, `mean_interface_plddt`, `pdockq`, `seed` — in addition to the standard contact map statistics. PDB structure files are written to the current working directory, named by protein pair ID.

Using `--plot` generates contact map plots as with the other commands:

```bash
$ yunta af2-single test/inputs/DYR_YEAST.a3m -2 test/inputs/CAPZA_YEAST.a3m -o test/outputs/af2-single.tsv --plot test/outputs/af2-single-plot
```

```bash
  msa1                  MSA file. Default: STDIN.

  -h, --help            show this help message and exit
```

#### Interspecies (host-pathogen) analysis

Use `--interspecies` / `-i` when the two MSAs come from organisms that interact as host and pathogen. `yunta` uses a built-in host-pathogen interaction (HPI) map to pair aligned sequences across species rather than requiring exact species identity:

```bash
$ yunta dca-single test/inputs/crypto/Q5CPK5_CRYPI.a3m \
    -2 test/inputs/human/EZRI_HUMAN.a3m \
    --interspecies --apc \
    -o test/outputs/dca-single-interspecies.tsv
```

By default (without `--strict-match`), the HPI constraint is relaxed for the query sequences themselves — useful when screening an uncharacterised query against a known host or pathogen proteome. Add `--strict-match` to require that query sequences come from species in the HPI map.

## Python API

Load and inspect an MSA:

```python
from yunta.structs.msa import MSA, PairedMSA

msa = MSA.from_file("my-msa-file.a3m")
print(msa)         # MSA(name=P07807) of sequence length 549, with 14246 sequences.
print(msa.neff())  # effective sequence count
```

Pair two MSAs and run DCA:

```python
from yunta.structs.msa import MSA, PairedMSA
from yunta.interactions.dca.dca_torch import calculate_dca

msa1 = MSA.from_file("protein-a.a3m")
msa2 = MSA.from_file("protein-b.a3m")
paired = PairedMSA.from_msa(msa1, msa2)
contact_matrix = calculate_dca(paired, apc=True)
```

For interspecies pairing, pass `interaction_map="builtin"`:

```python
paired = PairedMSA.from_msa(msa1, msa2, interaction_map="builtin")
```

Or supply a custom dict mapping species IDs to lists of interacting species IDs:

```python
paired = PairedMSA.from_msa(
    msa1, msa2,
    interaction_map={"NCBI:562": ["NCBI:10710"], "NCBI:10710": ["NCBI:562"]},
)
```

Run the full screening pipeline programmatically:

```python
from yunta.screening import dca_one_vs_many, rf2track_one_vs_many

outputs = dca_one_vs_many(
    msa_file1="query.a3m",
    msa_file2=["target1.a3m", "target2.a3m"],
    apc=True,
    interaction_map="builtin",  # omit for same-species
)
for result_matrix, interaction_matrix, metrics in outputs:
    print(metrics.ID, metrics.focality)
```

Each element of `outputs` is a 3-tuple `(full_contact_matrix, inter-chain_contact_matrix, metrics_dataclass)`. Metrics dataclasses (`DCAMetrics`, `RF2TMetrics`, `AF2Metrics`) can be written directly to TSV:

```python
metrics.write("results.tsv")
```
